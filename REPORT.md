# Звіт до лабораторної роботи №3

## Мета та варіант

Мета роботи — спроєктувати ієрархію класів із поліморфною обробкою через базовий тип і дотриматися принципу підстановки Лісков. Обрано варіант 4: базовий тип `Notification`, різновиди `EmailNotification`, `SmsNotification`, `PushNotification`, спільна операція `formatMessage`.

## Структура ієрархії

Абстрактний клас `Notification` містить спільні дані `recipient`, перевірку одержувача та метод `getRecipient()`. Метод `formatMessage(String message)` оголошений абстрактним, оскільки спосіб формування повідомлення залежить від каналу.

Кожен різновид має власне специфічне поле (`subject`, `sender` або `application`) і перевизначає `formatMessage`. Конструктор кожного нащадка викликає `super(recipient)`, тому спільна частина об’єкта ініціалізується централізовано, без дублювання перевірок.

Ключовий фрагмент клієнтського коду:

```java
Notification[] notifications = {
    new EmailNotification(...),
    new SmsNotification(...),
    new PushNotification(...)
};

for (Notification notification : notifications) {
    System.out.println(notification.formatMessage(message));
}
```

Масив і цикл працюють лише з `Notification`; перевірки `instanceof` та розгалуження за типами відсутні. Якщо додати, наприклад, `TelegramNotification extends Notification`, код масиву та циклу змінювати не потрібно — достатньо створити клас і додати його об’єкт до вхідних даних.

## Обґрунтування LSP

Кожен нащадок можна передати туди, де очікується `Notification`, тому що він має всі операції базового типу. Жоден нащадок не послаблює доступні можливості, не змінює контракт конструктора базової частини та не викидає несподіваних винятків для коректного повідомлення. Метод повертає рядок сформованого тексту для будь-якого підтримуваного каналу, отже очікувана поведінка клієнта зберігається.

## Відповіді на контрольні питання

1. Обробка через базовий тип прибирає залежність клієнта від конкретних класів і дозволяє додавати нові різновиди без переписування алгоритму.
2. Спільний контракт потрібно оголосити в базовому типі, а відмінності реалізувати через перевизначення методів у нащадках. Клієнт має працювати з базовим типом.
3. Принцип підстановки означає, що об’єкт нащадка можна використовувати замість об’єкта базового типу без порушення очікуваного результату. Перевірити це можна тестуванням клієнтського коду на всіх різновидах через посилання базового типу.
4. У базовий клас варто винести спільні поля, інваріанти, перевірки та поведінку. Специфічні дані й алгоритми слід залишити у похідних класах.

## Висновок

Створено ієрархію сповіщень із трьома різновидами. Поліморфний масив демонструє єдиний спосіб обробки, а використання `super` забезпечує коректну ініціалізацію базової частини. Архітектура відповідає принципу LSP і допускає розширення без зміни коду клієнта.
